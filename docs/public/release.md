# Release runbook

Release candidate construction, publication, and post-publish verification are separate boundaries. Never rewrite a published version or tag, replace a release asset, or expose private source history.

## Candidate

1. Confirm the private source is clean and matches its private origin.
2. Run `pnpm check`, `pnpm compatibility:check`, PostgreSQL integration, clean-room, browser, lifecycle/load, build, and audit checks.
3. Run `BETTER_REALTIME_RELEASE_EXPORT=1 pnpm package:export-public` and require `sourceMode: "clean_git_index"`.
4. Review the compatibility report and classify every detected outward change in `compatibility/changes.json` as `compatible`, `deprecated`, or `intentionally_breaking`.
5. Select the release boundary from the changed surface: compatible fixes/additions use the next unused `0.1.x-alpha` identity; fundamentally incompatible public API/configuration/semantics use `0.2.0-alpha.1`; an incompatible wire contract uses `better-realtime.v2`; PostgreSQL storage changes require a versioned migration. The unpublished alpha.2 tag-only attempt and alpha.3 tag-and-draft attempt are preserved, so the fix-forward release is `0.1.0-alpha.4`.

## Approval-gated publication

The next release uses npm OIDC Trusted Publishing only. The `npm-alpha` GitHub Environment keeps required manual reviewers. The package publishing setting remains `Require two-factor authentication and disallow tokens`, which continues to disallow token-based publishing; no npm token or bootstrap secret is accepted by the workflow.

`release.yml` receives an exact version, immutable release/tag source SHA, reviewed workflow SHA, approved lowercase SHA-256, and approved byte size. A first dispatch normally uses the same commit for both SHAs. When an immutable partial release requires a workflow-only fix-forward, the source SHA remains unchanged while the workflow SHA must be an explicitly reviewed descendant on `main`; package contents, tag target, Release notes, and artifact approval remain bound to the source SHA. The dispatch itself must run from `refs/heads/main`, and both the dispatch SHA and workflow-file SHA must equal the approved workflow SHA before checkout or repository-controlled tooling runs. Per-version concurrency prevents overlapping release runs. The workflow observes GitHub and npm before every transition. Existing state is accepted only as a partial-failure recovery boundary after its full identity is proven:

- the tag reference must point to an annotated tag object, not a lightweight tag;
- the tag object must have the exact name, message, commit type, and reviewed source SHA;
- drafts are discovered through the authenticated, paginated Release list and then bound to one numeric Release ID; the published-release tag endpoint is never used for draft discovery;
- an existing draft must retain the exact prerelease title, notes, target metadata, and every already-uploaded asset digest and size;
- an existing published release must already be the exact immutable prerelease;
- any other target, message, asset, lifecycle state, or duplicate npm version fails closed.

The workflow isolates trust boundaries in separate jobs. The build job has no OIDC permission and checks out the reviewed workflow SHA for the current control-plane checks. It separately checks out the immutable source SHA under `release-source` and builds the sole package tarball there, preventing a recovery-only workflow commit from silently becoming package source. Candidate gates and the deterministic public-export scan run on the reviewed descendant, while the exact source version and release notes are read from the immutable source commit. Immediately after packing—and before clean-room verification, artifact upload, tag creation, or any Release mutation—the job fail-closed compares the tarball digest and byte size with the separately approved inputs, verifies the exact checksum sidecar, and checks the pack report's size and file count against the manifest. It also emits a canonical identity record binding source, source release notes, file count, asset names, digests, and sizes.

The tested state-machine adapter—not workflow shell branching—discovers the authoritative Release list, requires a unique tag match, captures the create response's numeric Release ID, and uses that ID for every subsequent query, upload, download, and finalization. Missing approved assets may be added to an exact draft, but an existing asset is never replaced or deleted. Before finalization both assets are downloaded by asset ID and byte-compared with the approved files. Reruns and new dispatches re-observe state and skip already-successful identical mutations.

Only after the exact Release ID becomes immutable does a no-OIDC `prepare-publication` job run the tested state observer and produce a mutation-free publication plan. The following `npm-alpha` job alone receives `id-token: write`; it performs no checkout, package installation, repository script, or repository lifecycle execution. It uses the checksum-pinned Node 24.18.0 distribution's bundled npm 11.16.0 and verifies both versions. On its clean runner it independently re-fetches the numeric immutable Release, annotated tag object, exact two assets, publish-intent checks, and registry state; recomputes the canonical identity digest; and byte-compares both GitHub assets with the approved files. This re-observation also makes a failed-job rerun reject stale outputs or enter verification-only instead of creating a second intent. Only a fresh exact E404 state records the durable check-run intent bound to the current workflow run and attempt immediately before `npm publish`. If the command result is ambiguous, later runs block on intent plus E404 and never repeat publication; exact approved registry bytes enter verification-only. `npm publish --tag alpha --ignore-scripts` is the single npm mutation in the OIDC job, so package lifecycle hooks cannot execute inside the OIDC boundary. The tarball is passed as an existence-checked absolute workspace path; npm CLI requires a relative local tarball path to start with an explicit `./`, otherwise it may be parsed as a package or Git spec. Trusted Publishing cannot authorize a later `npm dist-tag` command; changing `latest` requires a separate interactive npm WebAuth/2FA session after full verification.

A recorded intent is never deleted. The only supported pre-registry abort recovery accepts an explicitly supplied prior run/attempt and proves all of the following before writing a paired `publish-abort` Check Run: exact Release identity, registry E404, the prior workflow-dispatch identity, a successful identity/re-observation/intent sequence, failure at the publish step, a skipped result-export step, the immutable prior workflow source containing the known bare-relative-tarball bug under the pinned npm version, and the exact archived job-log signature showing npm code 128 plus the derived Git `ls-remote` path and no registry-publish notice. The state machine allows at most one such abort and one subsequent active intent, and both its tested resolver and checkout-free OIDC re-observation reject duplicate marker names. Any unpaired abort, duplicate marker, second active intent, different failed step/log/workflow source, or non-404 registry state fails closed.

GitHub immutable releases must be enabled by a repository administrator before dispatch. The setting is now `enabled:true` for this repository. The default `GITHUB_TOKEN` cannot read the Administration-scoped repository setting, so the workflow still proves the property on the published asset-complete release before npm publication instead of accepting an unverifiable setting claim. If immutability is disabled later, npm publication is blocked and the visible GitHub prerelease remains a fix-forward record.

## Verification-only recovery

Post-publish verification is implemented by the separate `release-verify.yml` verification-only workflow. It has read-only repository and Actions permissions, no OIDC permission, and no publish command. It can be dispatched safely with the exact version, public tag, numeric Release ID, approved SHA-256 and byte size, immutable release source SHA, current reviewed verification workflow SHA, original publish workflow SHA, and the original publish run ID and attempt without repeating publication. A fresh publish passes the same SHA for both workflow identities. If verification itself is fixed later, only the current verification SHA advances; the original publish workflow SHA remains fixed to the provenance-producing run.

Before checkout or package installation, the verifier uses repository-explicit API calls to prove the immutable non-draft prerelease, exact Release target, annotated tag name/message/type/target, exact two-asset set, approved tarball digest/size, and exact checksum-sidecar bytes. It stores this evidence outside the checkout directory, then checks out the current approved verification workflow SHA, proves that the immutable release source is its ancestor, and reads package identity and release notes from the source commit before repository-controlled installation. It requires the GitHub asset and converged registry tarball to match the approved digest and size, then byte-compares them, runs the tarball clean-room, and cryptographically verifies npm signatures. The verifier also reads the exact original Actions run attempt through the GitHub API, requires its workflow path and head SHA to match the separately approved publish workflow identity, and fail-closed compares that SHA with the SLSA provenance subject before confirming the `alpha` dist-tag. The tag object and GitHub asset evidence independently bind the package to the immutable source SHA. Registry polling is bounded to 20 attempts at 15-second intervals. A timeout or mismatch fails without attempting publication or changing external state.

Before pushing a prepared public release commit, run `release:check-public-history` with `BETTER_REALTIME_PUBLIC_AUTHOR_EMAIL`, the immutable `BETTER_REALTIME_PUBLIC_ROOT_COMMIT`, and the current remote `BETTER_REALTIME_PUBLIC_BASE_COMMIT`. The check queries the canonical remote, requires its `main` to equal that base, and compares every existing annotated tag object and target with the checksum-pinned baseline. It permits exactly one English Conventional Commit appended directly to the base, preserves the unique root, rejects merge or extra local commits, validates every author/message and fetch/push URL, and rejects any unapproved ref or Git object regardless of object type. This append-only mode replaces the one-root-only bootstrap check used before the public repository existed; it never authorizes rewriting the root or an existing tag, or pre-creating the next release tag.

## Alpha.1 historical boundary

The published npm version and artifact for `better-realtime@0.1.0-alpha.1` are a non-republishable preservation baseline. Public annotated tag `v0.1.0-alpha.1` and its two release assets are checksum-verified and preserved by project policy. The repository setting was `enabled:false` when alpha.1 was published, and that historical GitHub Release remains `immutable:false`; GitHub does not enforce immutability for it. The repository setting is now `enabled:true`, but GitHub applies the setting only to future releases and does not change alpha.1 retroactively. The one-time packages-all bootstrap GAT path is permanently closed and absent from current workflows. The bootstrap credential was revoked, the GitHub Environment secret was removed, and token-based publishing is disabled. Functional OIDC publication remains unverified until a separately approved later version is published.

## Failure handling

Never overwrite a version, move a public tag, or replace an asset. Preserve the checksum and evidence, document the failure, and fix forward only when state cannot be reconciled safely. Reruns and fresh dispatches use the same observed-state planner. Lightweight or moved tags, changed messages, multiple matching Releases, changed Release IDs, mismatched or `starter` assets, and registry bytes that differ from approval are rejected. An immutable exact Release with no publish intent may proceed to publication; one with an existing publish intent and continuing E404 is ambiguous and blocks. If registry bytes already exist, only verification runs. If publication succeeded but verification failed, `release-verify.yml` resumes without publication authority. The executable release adapter also rejects mutation commands for the preserved alpha.1, alpha.2, and alpha.3 identities even if invoked directly with a crafted identity file.

The `v0.1.0-alpha.2` public annotated tag is a preserved tag-only failure record from run `29904933389`; no alpha.2 GitHub Release or npm package exists. The `v0.1.0-alpha.3` annotated tag and draft Release ID `358418104`, including its exact assets, are preserved from the later draft-discovery failure; alpha.3 is not finalized or published. Neither identity is moved, deleted, or reused. Publication fixes forward as `0.1.0-alpha.4`.
